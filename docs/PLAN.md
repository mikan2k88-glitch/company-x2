# Company X2 初期企画・設計
目標は、仕事探しから受注・制作・検品・納品・入金まで運営者の介入なしで実在の有料案件を1件完了すること。顧客の入力・合意は必要。口座・契約・認証など初期設定は運営者が行う。

## 初期実装と未実装
実装済み: 純粋な案件状態遷移、CSV完全一致重複除去と検品、Web窓口、SQLite案件保存、トークン付き成果物ダウンロード、重複受付防止、中断案件再開、構造化営業候補取り込みと適合判定、テスト、Supabase用初期DDL。
未実装: 外部営業先コネクター、AI、Supabase永続化アダプター、外部証拠検証、決済、返金。現在は収益を生む完成品ではない。Webはloopback限定のsandbox。

## 初期商品候補
CSV重複除去・整形を技術実証の候補とする。これは商品確定ではない。顧客データを評価式として実行しない。表計算ソフト向け出力では数式注入対策を別途設計する。入力サイズと行数に上限を設ける。

## 営業経路の選定
公開募集、登録済み顧客API、自社サイト集客を候補として調査する。対象サービスの公式API、利用条件、自動提案可否、納品と決済の経路を確認してから採用する。実在の発注者・募集URL・日時・予算・期限・連絡経路が必要。架空の顧客やAIの発想を案件として数えない。営業送信は明示された対象・経路・件数上限を設定してから開始する。
受注経路はまだ決まっておらず、最優先の未解決課題である。

## 構成
営業探索 → 適合判定 → 条件合意 → 与信確認 → 制作 → 検品 → 納品確認 → 決済確定。
AIは探索・質問・作業計画を担当し、価格・試行回数・予算・状態遷移はプログラムで制限する。
Supabaseに案件・イベント・成果物参照を保存。既存アプリと別スキーマを使い、既存テーブルを変更しない。
状態更新はversionによる比較更新とイベント記録を同一トランザクションで行う。外部操作は操作キーによる冪等性、応答不明時の照合、再起動後の復旧が必要。DDLだけではこれらは未完成。
決済・納品・合意の証拠はコネクターが外部サービスで確認する。AIが生成した真偽値だけで売上にしない。

## 失敗処理
一時障害は上限付き再試行。結果が不明な請求は再送前に照合。対応不能は辞退、制作失敗は与信取消、決済後は別の返金フロー。納品済み未入金は未回収として記録する。停止スイッチは新規外部操作を止め、既存の取消・照合を継続できる設計にする。

## 既存資産
Company X: API構造を参考、モック成功や固定粗利は移植しない。
Gateway X: 制作→レビュー→再生成、決済失敗の区別を参考。物理業務は初期対象外。
warashibe-ai: 保存部品とキュー設計を参考。
stock-warashibe: 証拠・状態遷移・監視の設計を参考。株取引コードは移植しない。

## 開発順序
1. 営業経路の実現性と商品適合性を調査する。
2. Supabase永続化、競合更新・二重処理・障害復旧を実装する。
3. Web注文・合意・ファイル受付・検品・納品を実装する。
4. AIと決済をsandboxで接続して障害を含む一連の処理を検証する。
5. 指定された実環境で小額の1件を実証する。モック売上は実売上に混ぜない。

## 成功条件
実在の顧客、合意した成果物、納品証拠、決済事業者の入金確認、実原価が揃い、運営者が途中の判断・制作を代行していないこと。金額の大きさよりこの証拠を重視する。
