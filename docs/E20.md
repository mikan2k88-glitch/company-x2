# E20 — 自動返金と返金照合

入金確認から24時間経過しても成果物が準備できない注文、制作・検品の再試行3回を使い切った注文を全額返金の対象にする。ready/deliveredは受領未記録でも期限返金の対象外。無料・未入金注文も対象外。

返金対象をDBで確保し、制作のリースを無効化してからStripe APIへ問い合わせる。注文ID固定の冪等キーで全額返金を要求する。要求前にPaymentIntent、入金額、JPY、注文・セッション・モードを確認し、既存返金の一覧も確認する。通信断や再起動後は永続予約とStripe側の一覧から再照合し、冪等キー保持期間経過後も追加返金を避ける。

署名検証済みrefund.created / refund.updated / refund.failedを受け付ける。通知オブジェクトを直接台帳に使わず、選択したテスト/本番キーで最新RefundとPaymentIntentを取得して照合する。Stripe Refundにはlivemodeがないため、PaymentIntentと注文のモードで検証する。重複通知による二重計上や、古いpendingによる完了状態の巻き戻りを防ぐ。Company X2へ結び付かない他アプリの返金は計上しない。

pendingは返金受付中、succeededだけが返金完了・金額集計に入る。failed/canceled/requires_action、部分返金、異議申し立て、照合不足は運営確認へ回し、新しい返金を自動作成しない。手動返金も同じ照合台帳へ反映する。旧注文のPaymentIntent未保存分は順次取得し、既存返金履歴を照合する。

管理画面には本番返金完了額、入金から返金を引いた額（手数料・税控除前）、返金状態別件数、各注文の返金状態を表示。顧客画面も返金受付中・完了・運営確認を表示し、返金対象のダウンロードと受領記録を停止する。

## 適用

019_live_payments.sqlの後に020_refunds.sqlを適用。出力のcompany-x2-e20-supabase.sqlには019と020を順に含める。初回のE19→E20適用用であり、E20適用後に019を再実行しない。020単体の再実行は可能。

020はE19の関数を非公開スキーマへ移して公開RPCをラップする。旧関数を一般ユーザーとservice_roleから直接呼べないようにし、新表にもRLSを適用する。通常pingはschema_version9のまま。refund_pingはrefund_schema_version20。SQL未適用でも起動・無料・テスト受付は継続できる。本番新規受付には020も必要。

Stripeの既存テスト・本番Webhookそれぞれに以下の3イベントを追加する（キーとURLは変更不要）:

- refund.created
- refund.updated
- refund.failed

自動返金は既存payment_workerから30秒ごとに確認する。無料Renderが停止している間は動かず、次回起動後に期限超過を検出する。24時間ちょうどの返金実行や無人での全例解決を保証しない。失敗・部分返金・異議申し立ては運営対応が必要。カードへの着金時間、Stripe残高不足、決済手数料の扱いはStripe側の条件に従う。

## 検証

模擬APIの返金成功/保留/失敗、モード混同、通信断・再起動、二重通知、金額不一致、期限と制作競合、再試行、納品済み除外を検証。実PostgreSQL CIでSQLの再適用、権限、照合台帳、期限とリース失効を検証する。実カード・実返金は実施しない。
