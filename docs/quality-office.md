# 品質・改善室

管理者画面 `/quality`、読み取り専用レポート `/api/company/quality`。現在は `company_x2/quality-ledger.json` をレビュー記録として使用する。自動監視や第三者認証ではない。

## 運用手順

1. 不具合・失敗分類・費用・実顧客受領などの根拠から課題を選ぶ。顧客本文やCSVを台帳・テストへ転用しない。
2. P0（重大障害）、P1（業務を阻害する課題）、P2（品質・効率）、P3（利便性）の順を基本とし、完了条件を記載する。
3. ブランチで改善し、人工データで再現・検証する。必要な独立検査を保持する。
4. PRで結果を確認し、根拠を添えて台帳を更新する。CI成功だけで本番確認・実顧客検証を確認済みにしない。
5. 本番で該当機能を確認し、日付と範囲を記録する。コード完成と事業成立は別に判定する。

`verified` には根拠が必要、`resolved` にも解決確認の根拠が必要。課題の解決件数だけでプロジェクトの検証完了とはしない。各段階の適用範囲をnoteに明示する。既存の確認済み項目も、仕様変更時には再評価する。

他アプリは接続前の評価対象として記載し、最新コードを確認せず品質確認済みとしない。他チャットへの指示送信や権限共有は行わない。自動収益システムとのデータ連携は未実装。

本番課金開始、一般外部送信、無料期限延長、予算増額の権限は持たない。台帳から運用設定は変更できない。
