# E29–E34 autonomous coordinator

E29 lists up to 20 open Issues per allowlisted repository (up to five), applies existing scope/source gates, and prepares durable inquiries. The run report distinguishes missing permission from unsuitable requests and source errors. This does not automatically add other websites or repositories.

E30 refreshes only original requester replies. Free verification and AI processing are accepted only by a reply consisting of `[company-x2: free verification accepted] [company-x2: AI processing allowed]` with no other conditions. The invitation is durable, limited to one per contact, and rechecked against current source and latest requester reply before posting. Initial inquiries and invitations share one attempt per UTC day. Ambiguous send outcomes are not automatically retried. Sending defaults off.

E31 signs the contact ID into a seven-day free intake grant. The server resolves the current accepted contact and attaches its source URL to the existing order; client-supplied source is overridden. These grants cannot create paid work and use 50KB/1,000-row limits. Existing plan acceptance, input/output safety, verified artifact hash, payment evidence and support holds still apply. The link records acquisition provenance; it is not identity verification of the requester. A mock source-to-delivery-and-receipt test covers the connection.

E32 uses a durable per-UTC-hour run claim with lease-bound completion, so web worker and authenticated scheduler cannot duplicate a successful hour. Failed/crashed hours remain visible; the next hour may run, while uncertain external messages remain held. Supabase Cron + pg_net can wake the fixed Render agent endpoint using a Vault-protected agent token. No local PC is needed. A free Render service still has cold-start delays and provider quotas; hourly timing is not a guaranteed deadline. Scheduler installation is separate from the portable schema migration.

E33 exposes existing live-payment readiness and explicit stop reasons on the company dashboard. Existing live/test checkout separation, refunds, sales-terms checks and the user's absolute refund-only requirement remain enforced. That requirement keeps live sales closed; this release does not remove it or claim a legal guarantee. Seller identity and necessary statutory disclosures are not generated by software.

E34 metrics count real paid live orders separately from test/free orders, successful live refunds and AI reservations. Metrics use the current UTC month's order cohort and AI reservations, not a complete cash accounting ledger. Configure `COST_USD_JPY`, `PAYMENT_FEE_RATE` (0–1), `MONTHLY_FIXED_COST_JPY`, optional `MAX_MONTHLY_LOSS_JPY` (default 1000), and `LIVE_PRICE_JPY`. Missing cost settings stop live readiness. Known excessive loss, refund rate >=20% with five live orders, or failure rate >=30% with ten orders also stop external sending. A bounded 50–10,000 JPY recommendation appears after ten live orders; it is not silently applied to accepted quotes. Prices remain fixed in existing plans. The cost estimate uses reserved AI spend and configured fee/fixed costs, not actual invoices; free accounts need zero fixed cost explicitly declared.

Protected APIs: GET `/api/company/autonomy`, POST `/api/company/autonomy/run`. The fixed agent endpoint accepts action `cycle` using its existing dedicated bearer credential. Neither API receives arbitrary URLs, scripts, external actions or user-supplied run IDs. Reports omit tokens, CSV and requester bodies. Service-only RPC `cx2_autonomy` and private tables use RLS and revoked direct access. Apply the autonomous_control migration before deploying.

Implemented stages are subject to those gates: no real sale is enabled, no unspecified external website is automated, and actual customer completion has not been demonstrated merely by mock tests.
