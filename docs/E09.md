# E06〜E09 — 検証運用

会社運用画面は `/company`。従来の加工画面は `/` のまま使えます。

## 実装と現在の限界

|段階|実装|稼働条件・限界|
|---|---|---|
|E06|探索候補の確認優先度と不足する証拠を表示|既存GitHub公開APIの最新最大30件。探索範囲は拡大していません。応募許可・報酬・受注は未確認|
|E07|OpenAIによる単一サービスの分類、範囲確認、予算予約|任意の有料機能。キーと予算が必要。CSVの値は送らず、依頼文だけ送信|
|E08|条件版と入力ハッシュを含む合意記録、永続制作キュー、検品、所有者専用納品、ハッシュ付き受領|無料検証とStripeテスト注文。外部募集からの合意・入力取得・応募送信は未接続|
|E09|StripeテストCheckout、署名Webhook、金額・通貨・注文の照合、重複排除、取りこぼしの定期照合、運用台帳|実決済キーは拒否。実売上・入金・営業実績は0。実取引対応の完成を意味しません|

1件の無料依頼を、計画→条件確認→受付→制作・検品→成果物受信→受領記録まで通せます。Stripeのテストでは、入金証拠の照合後に制作を開始します。Stripeを未設定のまま支払い済みにする操作はありません。

## Supabaseの追加SQL

`supabase/migrations/009_company.sql` 全文を、RenderのSUPABASE_URLに対応するプロジェクトのSQL Editorへ貼り付けて実行してください。ファイルパスではなく内容を貼り付け、全文を実行します。002適用済みが前提です。009は繰り返し適用可能で、company_x2内の新しいテーブルとcx2_company RPCを作ります。他アプリのテーブルや既存注文キューを変更しません。

確認:
```sql
select public.cx2_company('ping');
-- {"schema_version":9}
```

未適用でも従来の注文画面は動きます。会社運用画面は「受注DB / 設定待ち」と表示し、新しい注文の受付を無効にします。SQLを適用後、ページの「状態を更新」で利用可能になります。既存の起動コマンドは変更不要です。

## OpenAI設定

Renderに以下を設定します。秘密キーをGitHub、ブラウザーの入力欄、チャットへ貼らないでください。

|環境変数|値|
|---|---|
|OPENAI_API_KEY|OpenAI APIのプロジェクトキー|
|AI_ENABLED|true（初期値false）|
|AI_MONTHLY_BUDGET_MICRO_USD|例: 3000000 = 月3米ドル。初期値0|
|AI_DAILY_BUDGET_MICRO_USD|例: 100000 = 日次0.10米ドル。初期値0|

予算はUTCの日付・月で集計します。固定モデルは `gpt-4.1-mini-2025-04-14`。調査時の公式料金は入力$0.40、出力$1.60/100万トークンです。出力上限1,024トークン、依頼文4,000文字まで。送信JSONのUTF-8バイト数+4,096を入力トークンの保守的上限として予約します。予約は請求実額ではなく、余裕を含めたアプリ内の予算管理値です。価格変更時はコードの料金定数と予算を見直す必要があります。

日次・月次の両方に収まる場合だけ永続的に予約し、複数インスタンスからの同時呼び出しでも超過予約を防ぎます。同じ所有者・同じ依頼文の結果をキャッシュします。タイムアウトや不正出力でも予約を保持し、プロバイダー課金の有無が不明なまま自動で再実行しません。別のアプリや別のキーの利用費、OpenAIアカウント全体の請求はこの上限に含みません。

AIは処理候補だけを返します。モデルの判断は正しさを保証しないため、実行前に具体的な処理範囲を表示し、同意が必要です。モデルにはツール・URL取得・任意コード実行の権限がありません。複数処理・例外条件を含む依頼は非対応判定を求めます。

## Stripeテスト設定

|環境変数|値|
|---|---|
|STRIPE_SECRET_KEY|`sk_test_` から始まるテスト用キー|
|STRIPE_WEBHOOK_SECRET|Webhookエンドポイント固有の `whsec_` キー|
|APP_PUBLIC_URL|`https://company-x2.onrender.com`|

Stripeのテスト環境にWebhookを作り、URLを `https://company-x2.onrender.com/api/payments/webhook` とします。イベントは `checkout.session.completed` と `checkout.session.async_payment_succeeded` を選択します。WebhookにはアプリのBasic認証パスワードは不要です。生の本文とStripe-SignatureをHMAC-SHA256で検証し、5分以内のタイムスタンプだけ受け付けます。実モードのイベントとキーは拒否します。

画面の「Stripeテスト決済」を選ぶと、固定のテスト¥100の注文を作ります。Checkoutは注文IDを冪等キーとして作成し、通信断でも同じ注文で再取得できます。カード入力はStripe側だけで行います。戻りURLに所有者トークンは含めません。同じブラウザー・同じタブで戻るとsessionStorageの注文を再表示します。

支払い完了画面に戻ったことだけでは入金済みにしません。保存したCheckout ID、注文ID、金額100、JPY、paid、完了、testモードをすべて照合します。署名済みWebhookの重複を保存済みイベントIDで排除します。取りこぼしは最古の未処理セッションから最大3件、約60秒以上の間隔でStripe APIを読み直します。複数デプロイからの定期取得はDBロックで調整し、照合・制作は冪等です。

テスト決済待ちのCheckoutが期限切れになった場合は、新しい受付キーで新しい注文を作ってください。返金・紛争・本番会計・本番売上の処理は未実装です。このため本番キーは使用できません。アプリから自動の支払い・返金操作は行いません。

## 復旧と運用

制作は120秒のDBリースで処理し、期限切れは最大3回まで再取得します。古い処理の結果は拒否します。上限到達時は失敗として入力を消去し、運用画面へ残します。完成時も入力は消去し、計画・入力ハッシュ・成果物・イベントを保存します。再生成が必要な場合は元のCSVを新しい依頼として入力します。

ダウンロード時にブラウザーが受信したバイト列をSHA-256で検証し、所有者が一致する受領APIで記録します。受領済みでも再ダウンロードできます。この記録は顧客の法的な合意や、ファイルをディスクに保存した保証ではありません。

運用画面の予約金額はAI請求額とは異なります。テスト入金は実売上と分けて表示します。詳細のAPIにCSV入力や成果物本文を含めず、成果物は所有者トークン付きダウンロードでのみ返します。運用画面は既存のAPP_ACCESS_TOKENによる限定共有が前提で、顧客アカウント分離や一般公開向けの認証ではありません。

Renderの無料プランが休止している間は探索・制作・決済の定期照合も停止します。次の起動で再開します。24時間の無人稼働には常時稼働するサービスへの移行と運用条件の整備が必要です。料金が発生するプラン変更は今回行いません。

## API

- `GET /api/company/status`: DB準備、設定状況、台帳。設定準備と実際の外部API疎通は別。
- `GET /api/company/candidates`: 探索候補の順位付け。応募は行わない。
- `POST /api/company/ai`: requestとai_terms_accepted。所有者トークン必要。
- `POST /api/company/quote`: service_key、csv、payment_modeから計画。
- `POST /api/company/transactions`: 同じ入力・サービス・モード、plan_sha256、request_key、terms_accepted、任意source_url。
- `GET /api/company/transactions/{id}`: 所有者用進行確認。
- `GET /api/company/transactions/{id}/download`: 検品済み成果物。
- `POST /api/company/receipt`: idとdownload_sha256。
- `POST /api/company/checkout`、`/api/company/reconcile`: 注文id、所有者トークン。
- `POST /api/payments/webhook`: Stripe署名が認証。ブラウザーからの支払い済み申告は受付しない。

Webhook以外はBasic認証と、必要に応じX-Order-Tokenを使用します。
