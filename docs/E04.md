# E04: データ処理サービスの拡張

受付画面で4種類のサービスを選び、保存・制作・検品・納品まで処理できます。すべて無料のsandboxで、AI・応募・契約・実決済はまだ接続していません。

| サービス | 処理条件 | 納品 |
|---|---|---|
| CSV重複除去 | 行全体の完全一致。先頭の出現を残し、列名・値・順序を保持 | CSV |
| CSV空白整形 | 列名と値にPythonのstrip相当の前後の空白除去。内部空白・行順・重複は保持 | CSV |
| CSV → JSON | 列名をキーにしたオブジェクト配列。001や空欄も文字列で保持 | JSON |
| CSVデータ検査 | 空欄（空白のみも含む）・完全一致の重複行・数式のような値を報告。入力を変更しない | JSONレポート |

数式のような値は前方の空白を除いた先頭が `= + - @` の値です。マイナスの数値なども含む推測で、危険性の確定診断ではありません。実行・自動修正はしません。検査レポートには元の値を含めず、列名・件数・位置を出します。位置のサンプルは最大50件です。レコード番号はヘッダーを1とし、値内に改行があるCSVでは物理的な行番号とは異なります。

## 上限と出力

入力はUTF-8で1MB・10,000データ行まで。追加3サービスは最大200列です。列名は空欄・重複不可、各行の列数を統一してください。空白整形の結果、列名が同じになる場合は失敗として終了します。構造の壊れたCSVは推測して修復せず、処理失敗を表示します。
追加サービスはUTF-8 BOM付き入力にも対応します。JSONにはBOMを付けず、CSVはダウンロード時にUTF-8 BOMを付けます。出力本文は8MBまでで、長い列名が各JSON行に繰り返される場合も生成中に上限を検査します。

納品ファイルのSHA-256を画面に表示します。`download_sha256` はダウンロードした実バイト（CSVのBOMを含む）のハッシュです。旧`sha256`はBOMなしの成果物本文のハッシュとして保持します。E03以前に完了した注文は旧ハッシュのみを持ちます。

## 既存Renderへの反映

1. 現在使っているSupabaseプロジェクトのSQL Editorで、`supabase/migrations/004_data_services.sql` の**本文を全文**実行してください。パスだけを貼らず、文字の選択を解除して全文を実行します。
2. 次のSQLで確認します。

```sql
select public.cx2_services('ping', '{}'::jsonb);
```

結果は `{"schema_version":4}` です。旧注文RPCのschema_versionは2のままです。
3. Renderへ最新mainをデプロイします。Start Command、Supabaseキー、APP_ACCESS_TOKENの追加変更は不要です。
4. サービスの選択欄に4種類が表示され、「設定待ち」が付かないことを確認します。
5. 各サービスで依頼を作成し、成果物のダウンロードまで確認します。

004が未適用でも旧CSV重複除去・探索は継続します。追加サービスの選択肢は設定待ちとなります。`GET /api/services` はサービスの処理条件と利用可否を返します。Basic認証が必要です。`/api/health` は引き続き既存注文DBの状態を確認し、追加サービスの準備は `/api/services` で確認します。

## 検証用の入力

```csv
id,name,note
001, Alice ,
001, Alice ,
002,Bob,=SUM(A1)
```

- 重複除去: データ行3→2
- 空白整形: Alice前後の空白を除き、3行を保持
- JSON変換: idの001/002、空欄、数式文字列を保持
- データ検査: 空欄2、重複行1、数式のような値1

## 保存と互換性

追加3サービスは専用の `company_x2.service_orders/service_events` とservice-role限定RPCに保存します。旧workerは新サービスのキューを取得しないため、ローリングデプロイ中にJSON注文をCSV重複除去として処理しません。新workerは両方のキューを処理し、旧注文の進捗・ダウンロードも引き続き読み取れます。
注文のサービス種別と入力を保存し、再試行でサービスを変更できないように冪等性を検査します。旧・新キュー間で同じrequest_keyを使えないよう専用トリガーを追加します。旧RPCの定義と探索RPCは変更しません。他アプリのテーブルは変更しません。
新キューのleaseは120秒、上限3試行、未処理の受付上限は100件です。期限切れの旧workerは完了を書き込めません。失敗を成功・売上として扱いません。

## 探索との接続と残る課題

公開候補の選別も4サービスへ拡張しました。サービス名を候補ごとに表示します。語句による適合の推測で、受注の確定ではありません。契約・支払者・採算・入力仕様・AI作業と自動応募の可否は未確認として残します。取得済み候補の判定は次回の自動探索で更新されます。
この区切りは制作できるサービスの拡張です。実際の有料案件の獲得、自動応募、AI、決済は次の開発対象です。
