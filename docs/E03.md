# E03: 公開募集の自動探索

GitHubの公開Issue Search APIを毎時読み取り、CSVに関連するbountyラベル付きIssueの最新最大30件を保存・選別します。キーの追加登録は不要です。検索語は `is:issue is:open csv label:bounty in:title,body` に固定しています。

## この区切りでできること

- 実在する公開IssueのURL・本文抜粋・ラベル・取得日時・報酬表記を取得する
- 現在の完全一致CSV重複除去との適合を、範囲外・確認不足・要確認に分ける
- Web画面で候補、理由、報酬の記載、未確認条件を見る
- 成功時に候補一覧と探索状態を同一トランザクションで保存する
- 再起動後も結果と次回予定を保持し、複数デプロイ間で探索leaseを共有する
- 障害時は前回の結果を保持して古い結果であることを表示し、5分後に再試行する

報酬表記は本文中の通貨・金額の引用です。支払者の確認、支払保証、採算、利用条件、契約、入金の証拠ではありません。Issueに「bounty」と書いてあるだけで受注可能・売上としません。
CSV処理以外の研究・ソフトウェア改修は現在のサービスでは対応できません。選別はルール判定で、AIはまだ接続していません。原文はデータとして表示し、その指示を実行したりリンクや添付を取得したりしません。

## 既存Render環境への適用

1. 002を適用済みのSupabaseプロジェクトで、`supabase/migrations/003_public_scout.sql` の**内容を全文**SQL Editorへ貼り付けて実行します。パスを貼るのではありません。文字の選択を解除して全文を実行します。
2. 次で探索RPCの存在を確認します。

```sql
select public.cx2_scout('snapshot', '{}'::jsonb);
```

初回はstatusがwaiting、itemsが空配列になります。
3. mainの新しいコードをRenderへデプロイします。Start Commandは引き続き `python -m company_x2.server` です。既存のURLとSupabaseキーとAPP_ACCESS_TOKENを使用します。
4. 画面のE03表示と「仕事候補を自動で探す」を確認します。初回探索は起動直後に実行します。画面は毎分表示を更新します。

探索RPCの未適用・接続不良は画面に設定案内として表示します。既存のCSV注文は002のRPCで継続し、探索の未設定だけでアプリ全体を停止しません。`/api/health` は注文用DBの状態です。探索状態はBasic認証が必要な `/api/scout` で確認できます。

## 自動探索の動作条件

`SCOUT_ENABLED=false` で自動探索を停止できます。未設定では有効です。GitHub検索は匿名GETのみで、GitHubトークンや追加料金は不要です。探索leaseは180秒で期限切れとなり、古いworkerは保存できません。検索失敗は最短300秒後、成功は3600秒後に再取得します。探索用の保存件数は最大30件、本文は1件12,000文字までです。他の手動インポート候補は削除しません。

このスケジューラーはWebサービスのプロセス稼働中に動きます。Renderが休止している間は探索しません。再起動時に予定を過ぎていれば探索します。24時間の探索が必要になったら常時稼働workerへ移します。

## 検証と未完了の範囲

単体・HTTP・SQLiteテストと、CIの一時PostgreSQLで003の保存・排他・期限切れ・匿名アクセス拒否・旧RPC維持を検証します。公開APIを実際に読んで結果の形式も確認します。運営者のSupabaseへの003適用とRender上のE03確認は別途必要です。

自動応募、受注、Issueへの書き込み、外部連絡、AI生成、決済はこの区切りに含みません。将来はCSV加工への需要がある経路の追加と、制作可能なサービスの拡張、応募・契約・決済の条件確認が必要です。
